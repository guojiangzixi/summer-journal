# 版本更新指南

> 一句话总结：**签名决定「能不能升级」，版本号决定「系统认不认这是新版本」。**
> 这两件事搞错任何一个，用户就只能卸载重装（数据全丢）。

---

## 一、先分清三种「更新」

| 场景 | 谁在用 | 签名要求 | 覆盖安装保数据 |
|---|---|---|---|
| 自己开发调试 | 你 | debug 签名 | ✅ |
| 发同学验收 | 几个人 | 必须是**同一个**签名 | ✅ |
| 正式发布 | 所有人 | release 签名，**永不变** | ✅ |

关键：**同一个包名 + 同一个签名 = 能覆盖升级。** 只要有一个不一样，系统就拒绝安装。

---

## 二、签名：最重要的一件事

### debug 签名的隐患

Android 给每台开发机自动生成一个 debug keystore（在 `~/.android/debug.keystore`）：

| 情况 | 结果 |
|---|---|
| 同一台电脑上编的所有版本 | 签名一致 → **能一直覆盖升级** ✅ |
| 换一台电脑编 | debug keystore 是新生成的 → 签名不同 → **装不上，只能卸载重装，数据全丢** ❌ |

所以：**只要你打算长期更新，就必须换成自己的 release keystore。** 现在你手上的 debug 包，只能在同一台机器上迭代。

### 生成你自己的 keystore（只做一次）

```bash
# Windows：双击 generate-keystore.bat
# macOS / Linux：
./generate-keystore.sh
```

或者手动：

```bash
keytool -genkey -v -keystore summer-journal.jks \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias summerjournal
```

**三条铁律**（每一条都有人踩过）：

1. **`.jks` 文件和密码必须单独备份** —— 网盘 + 邮箱 + 移动硬盘，至少两处。丢了就**永远无法更新这个 App**，只能换个包名重新发（老用户全部流失）。
2. **绝对不要提交到 git**（`.gitignore` 已经帮你排除了 `*.jks` / `keystore.properties`）。
3. **绝对不要换。** 第一次用哪个，以后就必须一直用哪个。

### 工程已经接好了

`app/build.gradle.kts` 会自动读项目根目录的 `keystore.properties`：

| keystore.properties | `assembleRelease` 的产物 |
|---|---|
| 存在 | `app-release.apk`（已签名，可安装）|
| 不存在 | `app-release-unsigned.apk`（**未签名，装不上**，但能用来验证混淆是否正常）|

> 刻意设计成「没签名就产未签名包」，而不是「回落到 debug 签名」——
> 否则你迟早会把一个 debug 签名的包当成正式版发出去，那就再也升不上去了。

模板见 `keystore.properties.example`。

## 三、版本号怎么改

在 `app/build.gradle.kts` 的 `defaultConfig` 里：

```kotlin
versionCode = 2          // 整数，严格递增。系统靠它判断「这是新版本」
versionName = "1.1.0"    // 给人看的，随便起
```

规则：

- `versionCode` **只能变大**，不能变小、不能重复。
- 用户手机上已装的 versionCode ≥ 新包的 versionCode → **装不上**（报 `INSTALL_FAILED_VERSION_DOWNGRADE`）。
- `versionName` 不影响安装，但建议语义化。

| 改了什么 | 例子 | versionCode |
|---|---|---|
| 只改文案 / 样式 | 1.0.0 → 1.0.1 | +1 |
| 加了功能 | 1.0.0 → 1.1.0 | +1 |
| **改了数据库结构** | 1.0.0 → 2.0.0 | +1（**同时必须写迁移**，见第六节）|
| 内部测试版 | 1.1.0-beta1 | 也要 +1 |

一键升（同时改 versionCode 和 versionName）：

```bash
# Windows
bump-version.bat 1.1.0

# macOS / Linux
./bump-version.sh 1.1.0
```

## 四、标准发版流程

```
① 改代码
② 升版本号          →  bump-version.bat 1.1.0
③ 改了表结构就写迁移  →  见第六节
④ 构建              →  build-apk.bat release
⑤ 覆盖安装验证       →  adb install -r APK\SummerJournal-release.apk
```

第 ⑤ 步别跳过。**要专门验一件事：装完之后老数据还在不在。** 这是唯一能提前发现迁移写错的机会。

---

## 五、覆盖安装会不会丢数据

```bash
adb install -r APK/SummerJournal-release.apk
```

`-r` 就是 replace（保留数据）。手机上直接点新 APK 安装也是覆盖安装。

| 数据 | 覆盖安装 | 卸载重装 |
|---|---|---|
| 日程 / 课表 / 手札（Room 数据库） | ✅ 保留 | ❌ 清空 |
| 手札附件文件 | ✅ 保留 | ❌ 清空 |
| 设置 / 背景主题（DataStore） | ✅ 保留 | ❌ 清空 |
| 权限授权状态 | ✅ 保留 | ❌ 要重新申请 |
| **已排的闹钟** | ⚠️ **会被系统清空** | ❌ |

最后一条容易翻车：**App 一升级，系统会清掉所有 AlarmManager 闹钟。**

工程里已经处理了 —— `BootCompletedReceiver` 同时监听 `MY_PACKAGE_REPLACED`，升级后会自动重排全部提醒。但**权限得还在**（通知 / 精确闹钟 / 电池白名单），所以升级后建议进「我的」确认一下三项都还是「已开启」。

## 六、改了数据库结构怎么办（最容易出事的地方）

现在的策略是**按构建类型区分**：

| 包类型 | 行为 |
|---|---|
| debug | 允许「清库重建」—— 开发期改表方便，代价是本地测试数据没了 |
| **release** | **只认显式迁移**，没写迁移就直接崩溃 |

崩溃听起来很糟，但**比「静默把用户一学期的课表删光」好得多**。

### 正确流程

1. 改 Entity（加字段 / 加表 / 改类型）
2. `AppDatabase` 的 `@Database(version = 1)` → `version = 2`
3. 在 `AppDatabase.MIGRATIONS` 数组里加 `MIGRATION_1_2`
4. **写迁移测试**（用 `MigrationTestHelper` 跑一遍，确认老数据还在）
5. `versionCode` +1

### 加字段的模板

```kotlin
private val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        // ★ 必须给 DEFAULT，否则老数据这一列是 NULL，Kotlin 非空字段会崩
        db.execSQL("ALTER TABLE course ADD COLUMN credits INTEGER NOT NULL DEFAULT 0")
    }
}
```

### 加表的模板

```kotlin
private val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL(
            "CREATE TABLE IF NOT EXISTS exam (" +
            "id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL, " +
            "course_id INTEGER NOT NULL, " +
            "start_at INTEGER NOT NULL)"
        )
        db.execSQL("CREATE INDEX IF NOT EXISTS index_exam_course_id ON exam(course_id)")
    }
}
```

### 三个坑

1. **加字段必须给 DEFAULT** —— 最常见的崩溃原因。
2. **删字段 / 改类型不能用 ALTER** —— SQLite 不支持（3.35 以下完全不行）。要「建新表 → 拷数据 → 删旧表 → 改名」四步走。
3. **字段顺序要对上** —— Room 导出的 schema 在 `app/schemas/1.json` 和 `2.json`，改前后 diff 一下，字段名和顺序都要一致。

## 七、发版前检查清单

- [ ] `versionCode` 比上一版大
- [ ] `keystore.properties` 已配置（不是空着产出未签名包）
- [ ] 改了表结构 → 写了迁移 + 跑过迁移测试
- [ ] `apksigner verify --print-certs` 确认签名是**你自己的**，不是 `CN=Android Debug`
- [ ] 真机上**覆盖安装**后，老的日程 / 课表 / 手札还在
- [ ] 「我的」页三个提醒权限都是已开启
- [ ] 建一个 3 分钟后的日程，锁屏等到点，确认提醒照常响
- [ ] 更新日志写好了（模板见 `code/CHANGELOG.md`）

验签命令：

```bash
F:\Doc\SummerJournal\android-sdk\build-tools\35.0.0\apksigner.bat verify --print-certs 你的.apk
```

看 `certificate DN` 那一行：`CN=Android Debug` 就是 debug 签名，不能发。

## 八、常见报错

| 报错 | 原因 | 解决 |
|---|---|---|
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | **签名不一致**（换了 keystore，或换了电脑）| 只能用回原来那个签名；实在找不回就卸载重装（数据会丢）|
| `INSTALL_FAILED_VERSION_DOWNGRADE` | versionCode 没升 | 升 versionCode |
| `App not installed` / 解析包错误 | 同上，或包损坏、空间不足 | 检查 versionCode 和存储空间 |
| 升级后一打开就闪退 | 数据库迁移缺失或写错 | `adb logcat` 看 Room 的报错，补迁移 |
| 升级后提醒不响了 | 闹钟被清 + 权限丢了 | 进「我的」重新配三个权限，或重启一次手机触发重排 |
| 装完发现数据没了 | 迁移里写了清表逻辑，或用了卸载安装 | 检查迁移 SQL |

## 九、给你的建议路线

### 阶段一（现在）：debug 包自用 / 发同学

**保持现状就行。** 只要所有版本都在**同一台电脑**上编，就能一直覆盖升级。

唯一注意：别把 debug 包发到公开群里 —— debug 签名是公开的，任何人都能伪造一个同名同签名的包覆盖你的安装。

### 阶段二（准备长期用）：换 release 签名

做三件事：
1. `generate-keystore.bat` 生成 keystore
2. **立刻备份**（网盘 + 邮箱 + 移动硬盘）
3. 填 `keystore.properties`

然后 `build-apk.bat release`。

好处：包体小一半（R8 混淆裁剪）、运行更快、能上架、换电脑也能继续迭代。

### 阶段三（要上架）：AAB + 应用市场

```bash
./gradlew bundleRelease      # 产 app-release.aab，上架用
```

华为 / 荣耀应用市场走 AGC 上传，需要：
- 隐私政策（要列明：天气定位、媒体读取、教务系统 Cookie 仅本地、附件本地存储）
- `USE_EXACT_ALARM` 的用途说明（否则可能被拒）—— 写明「日历提醒类应用」

> ⚠️ **鸿蒙 NEXT 不兼容 Android APK**。如果要覆盖纯血鸿蒙用户，得单独用 ArkTS 重写，或做 H5 版本。
> 建议先在需求上想清楚：如果目标用户里鸿蒙 NEXT 占比不高，v1.x 只做 Android 是划算的。
